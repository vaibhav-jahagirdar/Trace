TRACE Product & engineering case study · 2026

An evidence pipeline for technical hiring

Better hiring input.
Stronger evidence.

Trace turns an ambiguous engineering hiring process into a structured, inspectable path from role definition to source-grounded interview decisions.

The premise

Hiring signal becomes weak when the input is weak. A generic job description creates generic evidence and leaves humans to resolve the uncertainty late.

Trace spends deeper computation only where stronger evidence is justified.

Read the system from input to interview
01 / The problem

Technical hiring breaks long before the interview.

The familiar resume-to-ATS flow makes it easy to collect applications and hard to compare real engineering evidence. Trace begins by making the hiring specification itself more precise.

01

Keyword saturation

Job-description terms become resume terms. The system rewards candidates for learning its vocabulary, then confuses vocabulary with capability.

02

Weak hiring input

Generic job descriptions hide the actual trade-offs: what is mandatory, what evidence matters, and what success should look like.

03

Claims outrun proof

“Built scalable auth” can describe anything from a token tutorial to a deliberate security boundary. Neither deserves the same interpretation.

04

Manual review does not scale

Founders and senior engineers spend weekends reconstructing context across resumes, repositories, files, and half-remembered comparisons.

02 / The thesis

Do not make the model more confident.
Make the evidence stronger.

03 / Define the role

Before evaluating a person, constrain what the role actually asks for.

Trace treats a job as an evaluation contract—not a block of prose. This makes the later scoring policy explainable because every requirement has an explicit origin.

01

Eligibility

Experience, education, notice period, authorization, visa, relocation, and geography.

02

Submission

Resume, repository, portfolio, project explanation, and the evidence an applicant is expected to provide.

03

Requirements

Technologies and concepts, divided into mandatory, preferred, and bonus.

04

Evaluation

Recruiter-selected dimensions and weights that shape claim-based Stage 1 assessment.

05

Evidence

Implementation, architecture, testing, domain, and other evidence categories worth deeper attention.

06

Success signals

Observable role-specific signs that a candidate could do the work—not generic AI assumptions.

Hard gates happen before expensive analysis

Ineligible applications stop with an explicit reason code; capability claims do not override a role’s non-negotiable conditions.

Strength and coverage are separate facts.

Strong local source is not broad proof. A complete scope may still reveal weak implementation. Private or unavailable work is represented as neutral—not silently translated into a negative score.

NOT SUFFICIENTImports, dependencies, README text, file names, stars, or repository size.
NOT ESTABLISHEDAuthorship, production use, scale, uptime, business impact, or runtime behavior.
07 / Scoring policy

The model produces structured evidence. The backend applies the decision policy.

Only canonical requirement mappings affect the numeric score. Engineering cards, claim verification, and material risks are retained for explanation, not double-counted as hidden penalties.

09 / System design

The product shape follows the failure boundaries.

Expensive model calls are treated as external, retryable computations. Raw responses are checkpointed before downstream validation and persistence, allowing recovery without automatically repeating expensive work.

10 / Honest boundary

Trace is designed to make an interview decision more defensible—not to replace the interview.

The system’s value is in making uncertainty explicit, focusing technical review on evidence, and turning visible source into better questions for a human reviewer.

Built in V1

01Structured six-part role definition and hard eligibility gates
02Claim-based Stage 1 analysis with checkpointed LLM output
03Repository discovery, targeted retrieval, and source-level verification
04Versioned scoring, provenance, and auditable shortlist records

Not claimed yet

01Empirically calibrated hiring predictions
02Proof of source authorship or production ownership
03Large-scale reliability, privacy, compliance, or SLA guarantees
04A replacement for recruiter judgment or technical interviews

Trace’s hypothesis

Hiring decisions improve when roles are defined precisely and evaluation moves from cheap self-reported claims toward expensive, source-grounded evidence.
Employer→Role contract→Eligibility→Claims→Evidence plan→Source verification→Audit→Human interview
